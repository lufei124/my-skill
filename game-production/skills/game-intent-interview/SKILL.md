# 目标澄清与设计追问

由 [game-production](../../SKILL.md) 在任何阶段按需调用。遵循上级指令、项目规范和用户当前授权。只有关键目标缺口才盘问；已明确的技术修复、配置修改不重新立项。

## 输入与入口

读取当前请求、已有决定、工程/原型证据、本轮范围与不允许改变的内容。输入不完整先自行检索已授权材料；不索要已知信息，不假装读过未访问的文件。

区分三层：
- 创作者与产品目标：为什么做、优先体验、制作范围、商业模式、成本与不可牺牲项。
- 目标玩家诉求：谁在什么情境下想获得什么；标记反馈证据与尚未验证的画像假设。
- 玩家游戏内目标：此刻要做什么、何时算完成、为什么值得做。

## 问题分诊

| 疑问 | 处理 |
|---|---|
| 事实：代码、配置、平台能力 | 先查现有实现或当前权威来源；查不到就标记具体缺口 |
| 目标：两项要求冲突或有不可逆取舍 | 追问用户的优先级，不擅自替用户拍板 |
| 效果：玩家是否理解、喜欢或回访 | 交给[玩法子 Skill](../gameplay-loop-design/SKILL.md)设计实验，不把用户猜测当玩家证据 |
| 可逆细节、不影响当前范围 | 标注假设继续，不扩大追问范围 |

## 追问协议

1. 先复述已经明确的目标与限制，提出最影响下一步的一个缺口；按依赖关系先问上游目标，不先问按钮颜色或字段名。
2. 默认一轮一个关键问题；只有互不依赖且确实必要时合并两三个。先解决当前阻断，不一次盘完整款游戏。
3. 用“观察/冲突 → 会影响的决定 → 合理选择及代价 → 推荐及理由 → 请用户决定”组织问题。允许第三种方向、暂缓或不知道。
4. 用具体游玩场景，不用 MDA、机制环等术语考试。不问“你觉得怎么才好玩”后把设计职责交回用户。
5. 不为了证明建议正确反复盘问。用户明确接受取舍后记录并执行；只有新证据或需求变化才重新打开该决定。
6. 必要决定未明时暂停依赖它的实现；能独立完成的只读检查和已授权可逆工作继续。用户要求先提案不提问时，提交带假设的可比较方案，不把假设升级为确认。
7. 停止条件：信息已足以决定本轮产物与最小验证，剩余不确定性已有负责人、验证方法或暂缓理由。不要用无限澄清替代行动。

## 两种访谈模式

**与制作人讨论**：给明确推荐和代价，由用户确定创作目标、商业模式和重要投入。可以用假设案例帮助比较，必须标为示例。

**访谈真实玩家**：先让玩家完成中性任务，观察真实行为，再问“刚才想做什么”“你以为会发生什么”。不要先展示推荐答案、替玩家解释成功、把口头喜欢当实际回访。参见[测试与证据](../../references/testing-and-evidence.md)。

## 返回与持久化

按[决策记录模板](../../templates/decision-record.md)返回：已确认目标、非目标、选择及代价、依据、待验证假设、受影响范围、下一步。未知信息保留未知，沉默不算同意。

沿用项目已有 ADR/进度入口；仅讨论时展示结论，得到项目写入授权后才保存。与旧决定冲突时记录替代关系与原因，不抹去历史，不把私人访谈写进公共参考库。

## 示例（虚构，不是项目现状）

用户说“让玩家更在乎家族成员”。先查已有体验目标，再确认优先观察哪种变化：能记住人物经历，还是愿意为特定人物牺牲收益。说明前者需要验证呈现与事件衔接，后者需要验证可理解的取舍；推荐一个最小验证而不是立刻新增好感度、礼物和每日任务。用户已选轻松观察时，不再诱导高压救人设计。
