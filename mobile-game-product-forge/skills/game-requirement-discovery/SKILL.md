# 游戏需求调研

负责移动游戏需求工坊的「需求调研 -> 需求摘要草稿」环节。通过用户访谈、项目知识、当前实现、历史证据、数据与用户反馈、必要外部调研和相关角色输入，建立可信现状，识别冲突、未知项和风险，把模糊想法推进到可由编排器发起需求理解确认的状态。

本子 Skill 是 `mobile-game-product-forge` 的能力拆分。跨阶段的状态所有权（需求处理模式、确认门、版本号、共享工作目录、多 Agent 协议）由编排器持有，本子 Skill 假设这些前置已成立，不重复其规则。

## 前置条件

1. 编排器已判定需求处理模式（模式1/2/3）。模式1或模式2需已读取项目知识库索引；模式3不读取项目知识。
2. 共享工作目录已建立。
3. 信息优先级与项目知识只读规则已在编排器生效。

## 输出合同

1. 调研结论与来源索引
2. 当前状态、目标状态及其差异
3. 冲突、未知项和风险
4. 建议复杂度与建议原型适用性
5. 需求摘要草稿
6. 需要用户确认的问题

本 Skill 不等待原型确认或豁免，不生成 `context-snapshot.md`，不修改跨阶段状态或确认状态。完成后把调研文件相对路径和版本连同上述结果交给协调 Agent；协调 Agent 先更新现有 `projectContext.status=completed`、`file` 和 `version`，再发起既有需求理解确认。在确认门通过前，不得输出 PRD 章节、规则编号、接口、配置表、验收 Case 或“仅供参考”的完整方案。

## 上下文加载

默认读取：`00-stage-state.json`（正式编排）、用户当前材料、当前项目知识索引、与本需求直接相关的当前模块知识、当前决策/术语账本，以及按复杂度要求的当前实际配置或实现证据。模式3不读取项目知识，但仍可核验用户提供的实现和外部约束。

不默认读取：整个项目知识库、完整需求目录、全部历史 PRD/原型/评审报告、已替代需求摘要、已关闭决策或与本需求无关的外部资料。按 [上下文加载合同](../../references/context-loading.md)「快速执行索引」中「需求调研」行的默认章节选择证据；发现冲突、高风险或无法确认当前事实时，按同一行的触发扩展章节自动扩大读取。

## 1. 需求调研

所有正式需求必须形成调研产物。新正式需求自动生成 `00-research-findings.md`，结构见 [交付模板](../../references/templates.md)「需求调研结论」；在返回 `completed` 证据前，文件必须非空并保留「当前现状、目标状态、当前状态与目标状态差异、风险、来源索引」五个稳定标题。历史需求只有 `00-project-context.md` 时视为旧格式调研产物，可以继续使用，但文件不得为空；需要进入新流程时由协调 Agent 基于旧文件补充新格式，不删除或批量迁移。L1 可以精简，但至少记录用户目标、当前规则、当前配置或实现核验、当前状态、目标状态、差异、风险和来源，不得完全跳过调研。

六类来源：

1. 用户访谈：目标、问题、范围、决策、限制。
2. 项目知识：背景、模块规则、配置、技术、数据、UI、术语、当前 PRD 与历史决策索引，并标记有效性。
3. 当前实现：页面与交互、客户端/服务端、配置、API、数据库、埋点、后台、线上/测试环境和现有设计稿。
4. 历史证据：历史 PRD、ADR、Git、旧原型、评审、事故修复与变更记录，按触发条件读取。
5. 数据和反馈：埋点、漏斗、留存、转化、实验、日志、客服、商店、用户、运营和测试反馈；无数据时写「当前缺少量化证据」。
6. 外部调研：平台、支付、订阅、广告、SDK、隐私合规、地区渠道、新商业化或内部无成熟方案时触发。政策/合规核查适用于目标地区和目标发布日期的官方规则；SDK/API 核查当前接入版本或已确认目标升级版本的官方文档；升级同时读取源版本、目标版本和官方迁移指南，并记录访问日期与适用性。

必须分开记录：文档描述、实际实现、目标设计。当前代码和线上行为只是现状证据，不自动等于正确目标规则。

调研深度：

- L1：用户输入 + 当前模块规则 + 当前实际配置或实现核验；不默认全量历史和外部调研。
- L2：用户、知识、实现、相关数据/反馈、必要历史和相关角色事实输入；涉及平台时补官方资料。
- L3：完整现状、历史、数据、技术约束、平台合规、多角色输入、异常/补偿/兼容/迁移及现状到目标差异；不受软预算限制。

访谈深度（轮次预算为收敛目标，非硬上限；关键决策未明不得为凑轮数强行收敛）：

- L1：目标 1–2 轮。13 主题裁剪：必问「为什么做、推荐产品方案、核心业务规则、本期范围」；「目标用户/当前问题/触发场景」并入为什么做，「状态和限制/异常和边界/配置表控制」并入核心业务规则，「目标设备与朝向/数据和成功指标」仅实际涉及时问。
- L2：目标 3–5 轮，按 13 主题依赖顺序推进。
- L3：按需，但每 5 轮向用户汇报进度（已确认/待确认清单）并提供批量确认选项。

### 已有模块迭代（模式1）：读取现状飞书文档

模式1下，主动请用户提供本次迭代模块的现状飞书文档（URL 或 token），了解项目背景：

1. 先 `lark-cli skills read lark-doc`，再执行 `lark-cli docs +fetch --doc "<url|token>" --doc-format markdown --scope full --format json` 读取正文（命令与 flag 见 [../references/feishu-publish.md](../../references/feishu-publish.md) 第 5 节）。
2. 未绑定 lark-cli 或未授权时不得静默跳过：按 feishu-publish.md 提示安装授权，或回退请用户直接粘贴文档正文。
3. 把读到的文档定义并入 `00-research-findings.md`，再与当前实现核验分栏记录，不把文档直接标成线上事实。
4. 与 `knowledge/requirements/<module>.md` 比对：内容不重复且有长期参考价值时，标记为「待归档」并记录来源；归档提案统一由 `game-knowledge-maintenance-proposal` 在 PRD 完成后产出（见 [../references/project-knowledge.md](../../references/project-knowledge.md) 第 6 节）；AI 不直接写入知识库。

模式3跳过项目知识读取，仍可使用用户本次资料、可核验的当前实现证据和必要的官方外部资料。

## 2. 需求访谈

按决策依赖顺序推进：

1. 为什么做
2. 目标用户
3. 当前问题
4. 触发场景
5. 用户任务
6. 目标设备与朝向（横屏/竖屏/自适应；横屏品类须先确认）
7. 推荐产品方案
8. 核心业务规则
9. 状态和限制
10. 异常和边界
11. 配置表控制
12. 数据和成功指标
13. 本期范围

重要问题格式：

```text
需要确认的问题：

推荐方案：
推荐原因：

其他方案：
A.
B.

该决定会影响：
- 页面交互
- 服务端逻辑
- 配置字段
- 数据统计
```

访谈规则：

- 每轮询问 1–3 个相关问题，优先问会改变整体方案的问题。
- 不重复询问资料已明确的内容。
- 直接指出方案风险，并给出推荐方案和其他可行方案。
- **用具体场景施压**（视情况）：就一个边界编一个具体场景逼用户精确（如「玩家在购买途中断网」「复活币耗尽时再死亡」「赛季切换瞬间在线玩家」「未成年在宵禁时段发起付费」），把模糊关系逼到可判定。游戏状态机边界尤其吃这条。
- **术语澄清**：用户用模糊或重载词时，立刻提出规范术语并给出 avoid 别名（游戏域高发：体力/能量、重启/复活/转生、账号/角色/存档、关卡/章节/赛季）。一次定一词，结晶即写入术语账本。
- **当场叫停矛盾**：与项目知识库、既有配置/字段、用户前后说法冲突时，立即指出并要求裁定，不放过。
- 每轮更新两本 inline 账本：
  - **决策账本**：已确认、待确认、已排除、选择理由、历史规则关系，以及对交互、配置、字段和数据的影响。
  - **术语账本**：规范术语、定义（1–2 句说“是什么”不说“做什么”）、avoid 别名、来源。访谈结束并入摘要「术语表」，长期决策性术语经知识维护提案落 `knowledge/glossary/`。
- **长期决策过滤**：已确认决策中，只有同时满足「难回退 + 无背景会困惑 + 真有取舍」的，标为长期决策候选，访谈结束后经知识维护提案落 `knowledge/decisions/`；其余只在本次摘要里记录，不进知识库。
- **收敛许可**：模型可在任意轮次给出整套推荐方案；未决且不改变整体方案的细节列入摘要第 16 项「待后置确认事项」，由用户在需求理解确认门批量裁定。会改变核心流程、核心规则或范围的关键决策不得后置——待后置事项不等于「待确认假设支撑 PRD」。

## 3. 需求摘要

输出《需求理解与方案摘要》：

1. 需求背景
2. 当前问题
3. 用户目标
4. 业务目标
5. 目标用户
6. 使用场景
7. 推荐产品方案
8. 核心用户流程
9. 核心业务规则
10. 状态和限制
11. 本期范围
12. 不包含范围
13. 成功指标
14. 术语表
15. 已确认决策（标注长期决策候选）
16. 待后置确认事项

**术语表**（第 14 项）：从访谈术语账本并入。每条含规范术语、1–2 句定义（是什么，不做什么）、avoid 别名、来源。只收本项目/本需求专属术语，不收通用编程概念。长期决策性术语（跨 PRD 复用、难回退）经知识维护提案落 `knowledge/glossary/`，本摘要保留本次快照。

**已确认决策**（第 15 项）：每条标注是否为「长期决策候选」--同时满足难回退、无背景会困惑、真有取舍三项的标「是」，访谈结束后经知识维护提案落 `knowledge/decisions/`；标「否」的只存本次摘要。

**呈现形式**：摘要以独立文档 **`01-requirement-summary.md`** 形式交付用户过目与确认，不在聊天里散落成逐条问答。渲染为结构化提纲（上述 16 项为骨架），关键决策点旁附推荐方案、备选与影响；不套用 PRD 的章节躯壳、不编 `R-###`/`AC-###`/配置表/字段名——那些在原型验证状态后才定稿。这份文档是确认门 1 的确认对象：用户对着它说「可以」「确认需求」「可以进入原型」才有效。

仅当用户目标、业务目标、核心流程、核心规则、本期范围和主要异常原则明确，且不存在阻塞原型的问题时，才交由协调 Agent 请求需求理解确认；六项已明确后，残留的非方案性细节列入「待后置确认事项」随摘要一并确认，不无限追问。

## 4. 完成与交接

仅当调研已形成来源索引、当前状态、目标状态、差异、冲突、未知项、风险和摘要草稿，且不存在未暴露的证据缺口时完成。本 Skill 返回调研文件相对路径、摘要文件（`01-requirement-summary.md`）相对路径、版本与需要确认的问题；协调 Agent 先把调研完成证据写入 `projectContext`，再使用既有需求理解确认门。确认后由协调 Agent 冻结摘要并判断原型适用性。调研状态更新不增加用户确认点。

原型确认或正式豁免后，由协调 Agent 汇总调研产物、确认摘要、决策和原型证据，生成目标为 `prd` 的 `context-snapshot.md`。不得再次调用本 Skill 承担快照生成。窄任务只返回调研结论和摘要草稿，不写正式流程状态。
