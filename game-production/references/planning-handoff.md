# 策划与制作交接

这是总控的专项分工与降级协议，不是另一个总控。只加载实际存在且与任务相关的外部能力。

## 策划能力的连接

若宿主确实提供 `game-design-planner`，先读取其实际入口；目标追问由本包负责，核心玩法问题路由到本包玩法子 Skill，再把结果交给现有系统、经济、PRD流程。若未安装，使用下表完成当前必要设计，不假造路径，不要求用户先安装才能继续。

| 专项 | 输入 | 必要交付 | 不应越界 |
|---|---|---|---|
| 系统规则/PRD | 已确认目标、玩法方案、当前实现 | 目标/非目标、触发、前置、状态变化、先后顺序、失败重试、验收 | 不把新增建议写成当前行为 |
| 数值经济 | 权威配置、资源与目标 | 单位、来源/消耗/转移、账本、边界、敏感性与测试假设 | 预留不是消耗，不自动调核心数值 |
| UI与视觉 | 玩家任务、信息、操作与风格资产 | 正常/取消/失败流程、信息层级、控件状态、目标设备原型 | 不把整张UI图片当可用界面，不擅改已定风格 |
| 技术验证/实现 | 最小体验、平台、现有工程 | 构建/SDK/存档/生命周期试验、可运行产物、实际结果 | 不把另一个项目的引擎和平台决定复制过来 |
| 商业化/运营 | 已定商业模式与循环 | 候选点位、奖励经济、频控、平台核验、指标与撤回条件 | 不替用户改变商业模式 |
| 测试与数据 | 规则与待验证假设 | 工程回归、试玩任务、实际证据、数据口径与限制 | 不把模拟用户当真人证据 |

## 交接包

每次只包含：本轮问题与范围、读取材料/版本、已确认规则、假设与未知项、预期产物、验收方法、禁止改变的内容、依赖谁的哪个决定。按需引用[决策记录](../templates/decision-record.md)、[玩法方案](../templates/loop-design.md)和[实验计划](../templates/experiment-plan.md)。

下游发现目标冲突时退回目标澄清，发现玩法后果变化时退回变更评审；普通报错交技术修复，不重开立项。不将“等待所有目标完全明确”设为一切工作的前置门槛。

## 变更控制

检查项目规范、分支与未提交修改。修改只在授权范围内，保留已有内容与基准，新增回归不削弱旧测试。需要大幅改规则、存档或引擎时先解释影响；用户已明确授权的决定不要重复询问。发布、提交、推送按本轮明确授权执行，不默认外部写入。
