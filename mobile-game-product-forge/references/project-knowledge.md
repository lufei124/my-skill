## 1. 定位与边界

`knowledge/` 保存项目长期有效、经人工维护的事实、规范和决策。它与交付目录分离：

- `knowledge/`：长期知识，AI默认只读
- `docs/prd/`：正式PRD
- `history/`：历史交付或版本记录
- 本次工作目录：访谈、原型、草稿、评审和校验材料

PRD内容、AI推断和评审建议不会因生成完成而自动成为项目知识。

## 2. 发现与读取

模式1或模式2按以下顺序：

1. 从当前项目根目录向上定位最近的 `knowledge/INDEX.md`。
2. 读取索引中的模块名称、状态、版本、更新时间、负责人和路径。
3. 只读取与需求直接相关的知识文件；不得为“可能有用”遍历全部知识库。
4. 记录实际读取的文件、版本或更新时间，写入交付文档来源信息。
5. 再读取用户本次提供的新资料；新资料与知识库冲突时按 [context-loading.md](context-loading.md)「三类权威来源模型」「冲突处理：当前状态、目标状态与改动」分类核验并显式报告，不把知识内容直接当线上事实或目标规则。

未找到 `knowledge/INDEX.md` 时，报告“项目知识库未初始化”，只使用用户本次提供的材料和通用 Skill 规范继续；不得读取未安装的知识包，也不得把普通项目文件自动认定为权威知识。

模式3跳过以上全部步骤。

## 3. 知识模块

| 模块 | 典型内容 |
|---|---|
| architecture | 产品边界、系统关系、公共能力、核心数据流 |
| modules | 商城、广告及后续业务模块的当前设计、历史版本、依赖 |
| ui | 页面框架、组件、布局、视觉、交互与适配规范 |
| config | 配置表格式、命名、字段、发布和兼容规范 |
| analytics | 埋点格式、公共属性、既有事件和指标口径 |
| glossary | 项目专属术语的规范词、定义、avoid 别名（跨 PRD 复用的 ubiquitous language） |
| decisions | 经确认的产品决策、原因、替代关系和影响 |
| requirements | 按模块归档的历史/现状需求文档（从飞书抓取），作为迭代参考上下文 |

状态建议使用：`有效`、`待补充`、`待复核`、`已废弃`。待补充内容不能作为已确认规则。

## 4. 缺失与冲突

- 缺少模块知识：列出缺失信息、受影响章节和需要谁确认。
- 知识过期：保留引用并标注版本风险，不擅自按经验更新。
- 多份知识冲突：列出来源、更新时间、冲突内容、影响和推荐采用项。
- 用户最新明确决定与知识冲突：本次需求以用户决定为准，同时输出知识维护提案。
- 已废弃知识：仅用于解释历史，不作为当前设计依据。

## 5. 知识维护提案

正常PRD流程只生成提案，不修改 `knowledge/`。提案格式：

```text
提案编号：
目标知识模块：
目标文件：
变更类型：新增 / 修订 / 废弃 / 替代
触发来源：
现有知识：
拟变更内容：
证据：
影响范围：
冲突与风险：
需要人工确认：
建议负责人：
```

本格式为知识维护提案的唯一权威，子 Skill 输出提案时不得缩减字段。

lazy-create 规则：目标知识模块在 `knowledge/INDEX.md` 无对应行时，提案须额外含一条「新增模块」子提案（新增 INDEX 行状态为「待补充」+ 创建空模块目录），先挂号后填内容，避免首个长期术语或决策结晶时遗漏模块登记。

人工确认并通过专门维护流程落库后，新版本才能作为后续需求的权威知识。

## 6. 历史需求归档

模式1（已有模块迭代）下，从飞书抓取的该模块现状/历史需求文档，按模块归档到 `knowledge/requirements/`，作为后续迭代的参考上下文。它与其他知识模块同属只读消费，但定位是“历史需求原文参考”，不是已确认规则。

归档规则：

1. 抓取：经用户提供的飞书文档 URL/token，用 `lark-cli docs +fetch` 读取（见 [feishu-publish.md](feishu-publish.md) 第 5 节）；未绑定时回退请用户粘贴正文。
2. 去重：先比对 `knowledge/requirements/<module>.md` 是否已覆盖同一文档/版本；已覆盖则只更新引用，不重复归档；内容有差异时按“知识维护提案”提出更新。
3. 提案：归档或更新仍走「知识维护提案」流程，AI 不直接写入 `knowledge/`；用户确认后由人工通过独立知识维护流程落库。
4. 文件格式：`knowledge/requirements/<module>.md`，开头写 header（来源文档 URL/token、抓取时间、所属模块、文档版本或更新时间），其后为抓取正文；多版本可按 `<module>-<version>.md` 并存。
5. 引用：后续迭代引用历史需求结论时保留来源路径；历史需求中的规则不等于当前已确认规则，需以 `modules/`、`decisions/` 等已确认知识或用户最新决定为准。

不归档：与现有 `requirements/<module>.md` 重复的内容、未确认草稿、临时评审意见。

## 7. 推荐目录

```text
project/
├── skills/
├── knowledge/
│   ├── INDEX.md
│   ├── architecture/
│   ├── modules/
│   ├── ui/
│   ├── config/
│   ├── analytics/
│   ├── glossary/
│   ├── decisions/
│   └── requirements/
├── docs/
│   └── prd/
└── history/
```

项目已有不同目录时不强制迁移；在 `knowledge/INDEX.md` 中登记实际路径即可。
