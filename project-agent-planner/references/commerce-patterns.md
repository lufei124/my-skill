# Commerce Agents：跨项目模式库

## 使用边界

本文件是参考模式摘要，不是可直接导入的运行框架。模式编号沿用用户提供的《AI Agent 架构复用指南》P1–P10，内容按核对到的官方文档与关键源码收窄。出处编号对应 [sources.md](sources.md)。

**已核对的仓库事实**：两个独立业务角色、统一工具执行器、后端契约、按需流程 Skills，以及三条运行路径。[S1–S5]

**本 Skill 的通用设计选择**：不限定行业，不强制两个角色，保留现有业务栈，默认方案先行。自 v1.1.0 起，只要推荐 Agent，默认必须采用 Claude Agent SDK，除非用户明确要求不用；这是用户指定的方案约束，不是原仓库要求。下面标为“迁移建议”的内容不宣称原仓库已经实现。

参考代码没有完成生产鉴权、完整授权和真实支付。输入围栏不等于绝对防注入，来源门不等于权限，先读后答也不保证模型的自由文本永不出错。三条运行路径的能力差异见文末。[S1、S5]

## 模式选择表

| 编号 | 模式 | 默认判断 |
|---|---|---|
| P1 | 主 Agent 与角色边界 | 一个会话一个主 Agent；独立角色需权限或职责依据 |
| P2 | Backend 接口抽象 | 接入业务系统时采用；复用已有服务而非直接暴露数据库 |
| P3 | Prompt / 工具描述 / Skill 分层 | 所有 Agent 方案都应明确规则归属 |
| P4 | 输入围栏与不可信数据处理 | 读取文档、网页、工具结果或外部文本时采用 |
| P5 | 来源门、限额、暂存审批 | 按写操作风险选择；鉴权和业务校验始终不能省 |
| P6 | 统一执行器与运行时解耦 | 默认必须 Claude Agent SDK；只有用户明确豁免才选替代；业务执行门仍共享 |
| P7 | 结构化呈现与服务端填充 | 展示业务实体/数值时采用；无界面时用结构化文本 |
| P8 | 结构化长期记忆 | 可选；有明确跨会话价值与删除能力才建设 |
| P9 | 有界委托 | 可选；独立复杂子任务收益足以抵消复杂度才采用 |
| P10 | Grounding：先读后答 | 价格、状态、政策、权限、指标等事实性回答采用 |

## P1｜一个会话一个主 Agent；角色不等于子 Agent

**参考事实**：购物与商家是面向不同人的两个角色，不是同一条对话互相交接。参考主循环没有通用路由器或角色接力；复杂流程由 Skill 承载。[S2、S3]

**迁移建议**：
- 写“谁拥有对话、谁拥有状态、谁能调用哪些工具”。用户侧和运营侧并存只是可能性，不是模板要求。
- 不要把检索、写作、校验、导出各拆一个常驻 Agent。能够在同一个权限范围内由工具完成的，就先用工具。
- 已有多 Agent 系统先评估效果与迁移风险；不要为了符合参考而立即拆除。

## P2｜Backend 是能力接口，不是通用远程控制入口

**参考事实**：每个角色以 Backend 接口接业务系统。会话传给后端方法，凭证由宿主持有；业务步骤顺序、资格和可执行性在后端判断。不能提供的数据返回缺失及原因，而不是占位零。[S3、S6]

**迁移建议**：
- 定义任务级能力，例如查询剧本、读取报表、暂存配置变更；名称来自当前项目。
- 身份/租户上下文由宿主注入，不让模型自由选择 `current_user_id` 或 `tenant_id`。管理员操作目标用户时，可传经过授权的目标实体标识，但它不能替代调用者身份。
- 通用结果建议包含 `status、data、source、as_of、limitations`；这是建议契约，不是原仓库所有工具的统一字段。
- 类型校验和字段白名单优于自由 JSON；不默认提供无限制 SQL、Shell 或任意 URL 请求工具。
- `absent` 从工具和流程索引移除；`stub` 保留明确不可用响应，依赖它的端到端流程不计入可用 MVP。[S3]

## P3｜规则只在合适的位置定义一次

**参考事实**：工具参数与调用专属规则放工具描述；多数轮次适用的规则放静态 Prompt；低频、多步骤流程按需加载 Skill。稳定提示词与动态上下文分开。[S2、S3、S9]

**迁移建议**：
- 输出一张规则归属表，而不是一份覆盖全部业务的巨型系统提示词。
- 为 MVP 场景列 Skill 名称、触发条件、流程、允许调用的工具、终止条件和输出。
- 事实数据不塞进静态提示词。工具集按部署/角色权限配置稳定，不为缓存复用而越权共享工具或用户上下文。
- 只在已选平台支持时设计具体缓存断点；不能把某厂商的缓存参数搬到其他 API。

## P4｜把不可信内容当数据

**参考事实**：第三方文本经过清洗、固定边界包装和长度限制；提示词将其定义为数据。`Fence` 是共享处理模块。[S5、S10]

**迁移建议**：
- 标清用户直接请求、可信宿主上下文、工具结果、检索文档、长期记忆的来源和信任等级。
- 对模型输入、界面输出分别处理；业务标识与数值保留类型，不能用破坏性文本清洗修改真实 ID。
- 限制文档长度、结果数和分页规模；截断时明确提示不完整，关键证据不足就继续查询或保留判断。
- 输入围栏只是降低攻击面；真正防止越权写入仍依赖工具白名单、后端授权、审批和测试。

## P5｜写操作的工程化边界

**参考事实**：写入接受本会话已查到的实体或已有业务状态中的目标；有可配置限额。商家写入先暂存，应用时再次检查护栏，并在默认配置下检查宿主审批标记。聊天文字不会设置该标记。[S5、S7、S13]

**迁移建议：风险分级**

| 类别 | 处理 |
|---|---|
| 读取 | 检查身份、租户和可读字段；避免泄露数据 |
| 低风险且可撤销的明确请求 | 权限、来源和业务校验通过后可直接执行，并提供撤销或补偿方式 |
| 删除、发布、资金、权限、批量或其他高风险动作 | 生成变更预览，经可信审批后执行；缺少审批能力时只交付草稿 |

**审批与执行建议**：
- 变更记录包括目标、前后差异、影响范围、数据版本、申请人、有效期及审计标识。
- 审批绑定具体变更 ID/内容摘要、范围及审批人。目标、内容、资源版本或权限变化后重新核验，必要时重新审批。
- 最终写入仍需 Backend 授权与业务校验；“这个 ID 查询过”不代表“这个人可以修改”。
- 新建实体先校验所属容器/父实体和创建权限；不能机械要求新对象 ID 已经存在。
- 原子状态迁移、幂等操作 ID、版本检查与持久审计是生产加固建议，不能只依赖进程内锁。
- 超时后先按操作 ID 查询结果；未知状态不得当失败重复提交。无法回滚时写出人工处置或补偿流程。

原仓库 `ToolOutcome.held()` 对应工具结果事件的 `status: blocked`，不要把方法名 `held` 与线上的状态值混用。[S5、S7]

## P6｜Claude Agent SDK 主运行层 + 共享业务执行门

**参考事实**：Messages API、Agent SDK 和 MCP 路径进入共享执行器，统一处理工具分发、错误、呈现、记忆等；具体角色保留自己的工具和校验。[S4]

**迁移建议**：
- 原仓库的三种路径是参考事实，不是本 Skill 要再次自由选择的默认菜单。没有用户明确豁免时，运行层确定为 Claude Agent SDK，详见 [sdk-runtime.md](sdk-runtime.md)。
- 复用项目现有业务调用链；主循环和上下文管理交给 SDK，业务工具通过自定义工具/MCP 接入共享执行门。不因已有多供应商客户端而改回自研 Agent 循环。
- 逻辑上分出运行层、角色契约、业务执行门、Backend 和业务系统，不强制拆成五个服务。运行时解耦指业务契约不被绑死，不是同时维护三套循环。
- 未知工具、参数不合法、无权限、业务冲突、数据不可用、超时分别设计可恢复结果。
- 不让 SDK 内置工具、MCP 或后台任务绕过业务安全门。每新增执行入口，重跑同一套安全契约测试。
- 能否导入 commerce-agents 原包取决于语言、依赖和契约；其他技术栈可迁移其业务接口/安全模式，但这不是重写 SDK 主循环的理由，不保证零成本迁移。

## P7｜模型给选择与解释，业务事实由服务端填充

**参考事实**：呈现工具接收实体 ID、排序及解释；服务端从本会话记录填充事实字段并输出 UI 事件。模型仍可提供理由/备注，不是所有界面文字都禁止来自模型。[S8]

**迁移建议**：
- 明确实体卡片、指标、状态、审批预览各由哪个现有组件渲染，避免从自由文本里正则提取真实业务数值。
- 服务端组装的数据也应带时间/版本，不能把会话快照当实时数据库保证。
- 无前端不强制开发卡片：可以把同一结构化结果渲染成文本。
- 创作型项目区分“生成内容”和“业务事实”。剧本、文案等可由模型生成；发布状态、额度、权限等不可编造。此项是跨领域适配，不是原电商 UI 的现成能力。

## P8｜会话、业务状态、长期记忆分开

**参考事实**：长期记忆是经过 schema 和写过滤器的结构化事实，支持保留、删除和清空。参考提取路径读取最后一轮用户/助手文本，不读工具结果。[S5、S7]

**迁移建议**：
- 会话保存消息、已见实体、当前步骤和预算；业务系统保存任务/变更/执行结果；长期记忆只保存经过允许的长期偏好。
- 记忆不是业务数据源，不保存权限、余额、token 或未经验证的推断作为事实。
- 默认不因“Agent 应该有记忆”新增数据库。有必要时明确作用域、类别、查看/更正/删除、保留期限与账号删除联动。
- 提取器不读工具结果仍不等于不会污染；助手的复述也要校验。删除期间的异步提取不得重新写回旧事实。

## P9｜受限委托，不是无限递归协作

**参考事实**：参考 Delegate 接收简报和受限上下文，输出 schema 校验结果；不负责写操作、直接呈现或递归委托。不同运行时实现能力不同。[S3、S5]

**迁移建议**：
- 说明为什么不能只用普通工具；给委托输入、只读工具白名单、结果 schema、超时、调用次数和成本预算。
- 主 Agent 负责综合与对话，可信执行入口负责写入；委托返回的 ID 不能自动扩大主会话可写范围。
- 图像/视频生成、转码、导出等长任务通常先建为任务服务：`提交 → job_id → 状态查询/通知 → 取消`。不可假定关闭对话后模型会继续执行。
- 如需可写子 Agent，它已经超出本参考的默认委托模式，必须单独论证授权、审批和审计。

## P10｜Grounding：事实回答先取证

**参考事实**：部分意图由规则触发读取；Messages API 可强制首个工具，SDK 仅预取具有预取形式的规则。原实现按规则优先级选择首个匹配项，并非覆盖所有语义。[S5、S11]

**迁移建议**：
- 为项目事实域列“问题类型 → 权威源 → 必要读工具 → 数据新鲜度 → 缺失时回复”。
- 查询结果同时约束自由文本和卡片；禁止将检索失败解释为数字 0、空库存或已删除。
- 工具暂存成功只能说待审批，提交任务成功只能说已提交，实际生效要以可信执行结果核验。
- 关键词规则会漏判；业务前置步骤仍放代码。先查再答不等于完全消除错误解释。

## 原仓库运行时差异：作为历史参考，不作为默认选型菜单

以下沿用 v1.0.0 核对到的参考适配器状态，不代表 SDK 当前产品能力上限，也不是第三方模型的通用保证。本轮未重新审计这些适配器。默认 SDK 方案应验证并补齐所需安全能力，不因差异自动转为其他运行框架。[S5]

| 能力 | Messages API | Agent SDK | Managed Agents |
|---|---|---|---|
| 工具内的围栏、来源门、限额等 | 共享执行器 | 共享执行器 | MCP 进入共享执行器 |
| Grounding | 用 `tool_choice` 强制匹配规则 | 仅有预取形式的规则；非全覆盖 | 没有同等代码强制 |
| 分析 | 参考只读分析委托与查询/预算限制 | 只读子 Agent，缺少同等查询工具和预算 | 参考 manifest 未声明分析工具 |
| 轮后记忆提取 | 支持，宿主调用更新入口 | 不自动等同于前者，需宿主接入 | 参考路径仅通过保存工具写入 |
| 默认审批实现 | 宿主可信标记 | 宿主/控制台可信标记 | 平台 `always_ask` 承担审批，服务端相应关闭宿主标记检查 |

生产方案不得简单关闭审批开关以兼容运行时。必须指出替代机制由谁执行、凭证如何绑定操作，以及如何验证不可绕过。
