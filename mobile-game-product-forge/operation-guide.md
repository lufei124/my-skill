# mobile-game-product-forge 操作指南

本文面向产品经理、产品负责人和需求协作角色。setup 会把本模板复制到目标游戏项目：

```text
docs/mobile-game-product-forge/operation-guide.md
```

项目内版本供团队日常使用；内容不同时 setup 不静默覆盖。

本文只讲日常操作。装插件、SSH 配置、升级和安装类故障排查见 Skill 仓库的《安装与升级指南》（`install-guide.md`），不在本文重复。

## 5 分钟快速开始

### 第一次使用：初始化一次（每个项目一次）

前提：Skill 已装好（装法见《安装与升级指南》）。在游戏项目根目录：

```text
请使用 $setup-mobile-game-product-forge 初始化当前游戏项目。
```

初始化会预览目录、知识档案、操作指南和飞书交付策略，等你确认后才写入。setup 不写项目 `AGENTS.md`、`CLAUDE.md` 或 `.cursor/` 规则。

### 每个新需求：一句话启动

```text
使用 $mobile-game-product-forge 开始一个正式需求。

需求名称：
初始想法：
已有材料：
负责人：
```

Skill 会自行创建需求目录和 JSON 状态、判断模式/复杂度/原型适用性、整理当前阶段上下文、执行机器门禁，并在需要产品确认时停下。默认不要求你重复十条流程规则，也不要求你手工整理全部材料。

### 中断后继续

```text
使用 $mobile-game-product-forge 继续需求：
history/<日期>-<需求简称>/
```

Agent 应先读 `00-stage-state.json`，再报告当前阶段、已完成、缺失和下一步。

## 1. 正确入口

正式需求从根编排器 `$mobile-game-product-forge` 启动。自然语言“设计一个系统”“增加/修改一个功能”“优化已有模块”“继续这个正式需求”“写正式 PRD”，以及没有明确限定阶段的宽泛请求，都应优先进入根编排器。只有明确说“只调研 / 只做原型 / 只评审 / 只补埋点 / 只发布”时才直接进入对应子 Skill。

`$game-prd-writing` 和 `$game-prd-publish` 是显式子任务入口，不能绕过正式状态。直接调用 PRD 写作且门禁不满足时返回 `BLOCKED`；只有明确要求“纯文档草稿/非正式 PRD”时才可输出带 `narrow_task` 标记的非正式产物。

正式流程：

```text
初始化一次
→ 一句话启动需求
→ 判断模式和复杂度
→ 多来源需求调研与摘要草稿
→ 确认点 1：需求理解确认
→ 判断原型适用性
  有交互：required，生成并确认原型
  无交互：not_applicable，产品负责人确认原型豁免
→ 生成 PRD
→ 按复杂度动态评审
→ 确认点 3：重大评审争议确认（仅有争议时）
→ 校验并冻结终稿
→ 正式 PRD 流程完成
├─ 知识维护提案（L1 默认不做；L3 必须评估）
└─ 按项目交付策略发布飞书
```

飞书不是第四个产品确认点。PRD 完成是 `prd.status=final` 且 `validation.status=passed`；飞书失败不会回退 PRD。

## 2. 首次初始化（每个项目一次）

本节是「5 分钟快速开始 → 第一次使用」的详细控制版，覆盖同一个动作；机器级安装/升级不在本节，见《安装与升级指南》。如需详细控制，可使用：

```text
请使用 $setup-mobile-game-product-forge 初始化当前游戏项目。

先探测并预览，不要立即写文件。
让我选择 core 或 core + 项目知识包。
确认 docs/prd/、history/ 和操作指南位置。
询问飞书是否为项目强制交付策略。
不覆盖已有知识、指南或人工维护文件。
```

初始化完成时 Agent 必须告诉你：

- 安装档案、Skill 版本和冲突；
- 操作指南：`docs/mobile-game-product-forge/operation-guide.md`；
- 正式 PRD：`docs/prd/`；
- 过程材料：`history/`；
- 飞书是否为强制项目交付策略；
- 一句话启动方式。

## 3. 需求模式、复杂度和原型适用性

### 需求模式

| 模式 | 含义 |
|---|---|
| 模式1：已有模块迭代 | 读取并复用已有模块知识 |
| 模式2：新增独立模块 | 读取架构和相邻模块，设计接入边界 |
| 模式3：通用规范模式 | 不读取项目历史；仍执行需求确认和原型判断 |

### 复杂度

协调 Agent 推荐，产品负责人可以调整：

| 级别 | 默认流程重量 |
|---|---|
| L1 小改动 | 精简摘要/PRD；原型或豁免；1–2 个直接专业角色；协调 Agent 做轻量标准/保真检查，不为横切轴另启 Agent；不机械创建所有文件；不默认知识提案 |
| L2 普通需求 | 标准确认、原型或豁免、动态相关角色评审、完整横切检查、校验终稿 |
| L3 核心系统 | 完整上下文和决策追踪；原型通常必需；全部相关角色、完整横切检查与重大风险识别；必须评估知识提案 |

复杂度不删除产品确认点，也不自动决定是否需要原型。

### PRD 研发执行结构

新 PRD 固定使用同一套研发执行结构：功能说明、总体流程、功能规则、页面和交互（按需）、接口/数据/配置（按需）、异常和边界、验收标准。L1/L2/L3 只改变深度，不再维护 20 章清单或章节裁剪说明。

“实现目标”只写功能要实现的结果；只有增长、商业化或实验类需求才补指标。多模块先列“涉及模块”及影响范围，正文仍按统一流程和 `R-###` 规则组织。客户端、服务端、数据库、配置和埋点不能被拆成独立功能模块；只有形成独立业务闭环时，才在功能规则内按业务能力分组。

项目不设计运营后台，运营调整统一写配置表。图形按问题选：业务分支用流程图，多页面用页面流转图，多端调用/回调用时序图，有生命周期用状态机图，多业务模块职责不清用模块关系图，多数据源用数据流图。简单需求用文字步骤。

### 原型适用性

以下变化必须生成并确认原型：新页面、入口、主路径、按钮、弹窗、状态反馈或交互变化。

无 UI/交互变化的服务端规则、配置/频控、数据口径、埋点、白名单/国家规则、订单补偿或纯技术兼容，可以正式豁免。产品负责人必须明确确认原因；Agent 不得自行豁免。豁免可与需求摘要同轮确认，不是 `narrow_task`。

## 4. 工作目录与 JSON 状态

默认：

```text
history/<日期>-<需求简称>/
```

按复杂度和实际阶段创建：

```text
00-stage-state.json
context-snapshot.md
00-research-findings.md
01-requirement-summary.md
01-requirement-decisions.md
02-prototype/index.html
03-prd-v0.1.md
04-review-report.md
05-prd-v0.2.md
06-lint-report.md
07-prd-final.md
08-delivery-record.md
09-knowledge-proposals.md
CHANGELOG.md
```

`00-stage-state.json` 是唯一跨阶段状态源，根编排器唯一写入，子 Skill 只读。`00-research-findings.md` 是新需求的调研记录，系统自动汇总当前现状、实际实现、目标状态、数据反馈、冲突和来源；旧需求的 `00-project-context.md` 可继续保留。所有正式需求（包括 L1）都必须有非空调研产物；新格式还会检查当前现状、目标状态、差异、风险和来源索引等最低结构，防止空文件冒充已完成调研。完成后系统记录 `projectContext.status=completed`、文件相对路径和版本，再进入需求理解确认。`context-snapshot.md` 只从调研和确认产物提取某个阶段需要的摘要与证据索引。二者都不是新的确认门。L1 不机械创建其他无关过程文件；原型豁免时不创建假原型；交付非必需且未执行时不创建交付记录。

历史 `00-stage-state.yaml` 不强制迁移。继续旧需求时 Agent 应提示“旧状态格式”，核对实际证据后新建 JSON，保留旧 YAML 不覆盖。

### 自动整理和补充来源

系统默认使用当前有效版本。L1 至少核验当前配置或实现；L2 按需补数据、反馈、历史和角色事实；L3 主动核查完整现状、平台合规、异常、补偿和迁移。证据不足、来源冲突或支付/账号/资产等高风险需求会自动扩大读取。你无需手工生成调研文档或快照、判断 metadata 完整性、选择每个评审角色的文件或计算 Token。

需要补充或追溯时直接说明：

```text
补充来源：<文件、飞书链接或正文>，请更新当前证据索引。
请追溯 <规则/决定> 的历史版本和来源。
请对 <支付/账号/资产等模块> 做深度核查，不要只依赖摘要。
```

系统应先定位相关文件和章节，必要时再扩大读取；不会因为上下文预算而跳过必要证据。

## 5. 机器门禁

| target | 条件摘要 |
|---|---|
| prototype | 调研完成且证据有效；需求摘要已确认且证据有效；原型适用性为 required |
| prd | 调研与需求摘要证据有效；required 原型确认、版本一致且 metadata COMPLETE，或 not_applicable 豁免证据完整 |
| review | PRD 为 draft/in_review，文件和版本存在 |
| validation | 评审通过；`openP0` 显式为整数 0；评审和 PRD 证据存在 |
| final | 校验通过；报告存在；目标 PRD 版本一致 |
| publish | PRD final 且校验通过；非强制交付返回 NOT_REQUIRED |
| delivery | 强制交付时要求 published、交付记录和发布时间 |

门禁退出码：`0=PASS/NOT_REQUIRED`、`2=BLOCKED`、`3=INVALID_STATE`。调研尚未完成是 BLOCKED；声明 completed 却缺文件/版本、文件不存在或文件名无关是 INVALID_STATE。metadata 提取单独使用 `0=COMPLETE`、`2=INCOMPLETE`、`3=INVALID`。required 历史原型会按结果定向回读 HTML、补齐 metadata 并重跑门禁；补齐失败返回原型阶段。not_applicable 豁免路径不读取 HTML，也不要求 metadata。

阻塞输出：

```text
BLOCKED
target:
currentStage:
missingConditions:
invalidFields:
returnToStage:
nextAction:
```

门禁失败时不能同时输出正式下游产物。

## 6. 三个产品确认点

### 6.1 需求理解确认

```text
需求确认。按当前目标、范围、核心流程和异常原则继续。
```

如需修改：

```text
需求暂不确认。请修改以下内容，修改后重新给我确认，不要进入下游阶段：
1.
2.
```

### 6.2 原型确认或豁免

有交互变化时实际打开 `02-prototype/index.html`：

```text
交互确认。冻结当前原型版本，可以进入 PRD。
```

无 UI/交互变化时：

```text
确认本需求不涉及 UI 或用户交互变化，同意原型豁免。
豁免原因：
批准人：
```

### 6.3 重大评审争议确认

只有实际出现重大争议才需要本次确认。无重大争议、P0 为 0、P1/P2 均有处理结论且无需返回原型时，协调 Agent 会直接通过评审，并汇报角色覆盖、问题摘要、已修改项和遗留项。

```text
P1-003：选择方案 B。
P1-006：本期不处理，记录为后续项。
其余按推荐方案修改。
```

有重大争议时评审状态为 `disputed` 并暂停，等待产品负责人决定；页面、入口、主路径、按钮、确认步骤、弹窗结构或关键状态变化也属于重大争议事项。裁定改变交互后，先退回原型重新确认，再更新 PRD 并只重审受影响部分。详细状态合同见 `references/stage-gates.md`。

## 7. PRD 完成与飞书交付

校验通过后：

- 工作目录保留 `07-prd-final.md`；
- 正式终稿同步到 `docs/prd/<需求简称>.md`，同步位置记录在状态 `prd.syncedTo`（机器门禁核验该文件存在，未同步不得冻结终稿）；
- `prd.status=final`，正式 PRD 流程完成。

之后知识提案与飞书交付互相独立。项目策略为：

- `delivery.required=false`：`status=not_required`，无需飞书即可完整完成 PRD；
- `delivery.required=true`：调用 `$game-prd-publish`；成功写 `published`，失败写 `failed`，PRD 仍为 final。

### 终稿后修订（重开）

终稿后需求发生内容变化时，由根编排器执行「终稿后重开修订」（见 `references/stage-gates.md` 标准状态迁移）：记录重开原因 → `prd.status=in_review`、bump PRD 版本、校验状态重置 → 只重审受影响部分 → 重新校验并冻结终稿。`docs/prd/<需求简称>.md` 同步件在新终稿冻结后覆盖更新；已发布的飞书文档不回收、不回退 `delivery` 记录，新终稿按项目交付策略重新交付并更新交付记录。

## 8. 窄任务

窄任务产物顶部标记：

```text
执行模式：narrow_task
完整流程门禁：未执行 / 不适用
已验证输入：
未验证输入：
```

常用入口：

- 只做原型：`$game-prototype`
- 只评审 PRD：`$game-prd-review`
- 只做埋点：`$game-analytics-design`
- 只发布终稿：`$game-prd-publish`
- 只校验：运行 `lint-prd.py`

窄任务不得称为经过完整确认链路的正式终稿。

## 9. 严格模式 / 故障排查提示词

默认启动不需要下面这些规则；仅在 Agent 跳步或状态异常时使用。安装、升级、SSH、版本类故障不在本节，见《安装与升级指南》第 3 节。

```text
使用 $mobile-game-product-forge 处理需求目录：
history/<日期>-<需求简称>/

先读取 00-stage-state.json 和实际文件。
核对当前阶段、模式、复杂度、原型适用性、最后确认版本和阻塞项。
机器门禁未通过时只输出门禁结果，不生成下游产物。
先报告“当前阶段 / 已完成 / 缺失 / 下一步”。
不重复已确认阶段，不自动提升状态。
```

## 10. 多人和多 Agent 协作

1. 一个需求一个目录、一个协调 Agent、一个 JSON 状态；
2. 只有协调 Agent 可以更新状态；
3. 其他 Agent 只提交阶段产物、问题或建议；
4. L1 不默认启动完整角色集；
5. 多人不能同时修改状态文件；
6. 已确认快照写入文件，不依赖聊天记忆；
7. 终稿后的内容变化开启新修订轮次（见第 7 节「终稿后修订（重开）」）。

## 11. 完成检查

```text
[ ] 根编排器启动正式需求
[ ] 00-stage-state.json 为 schemaVersion 1.1
[ ] 需求模式、复杂度和负责人已记录
[ ] 需求摘要 confirmed，文件和版本存在
[ ] required 原型 confirmed 且 metadata/版本一致，或正式豁免证据完整
[ ] 评审角色数量与 L1/L2/L3 相称
[ ] review.openP0 显式为整数 0
[ ] validation passed，报告与当前 PRD 版本一致
[ ] prd final，终稿已同步 docs/prd/
[ ] 知识提案按复杂度决定/评估
[ ] delivery 非必需为 not_required；必需时 published 或明确 failed
```

用户询问“怎么开始”“怎么继续”“现在进行到哪里”“这个 Skill 怎么用”时，Agent 应优先读取本项目指南和当前需求 `00-stage-state.json`，再回答。
