# 游戏制作总控

将已有策划转成玩家可以操作、制作人可以判断、下一位协作者可以继续的成果。围绕一段具体体验逐步决定玩法、表现和技术投入。

## 1 接手项目

1. 读取用户本轮要求、项目入口、现有制作进度、相关策划、最新配置和实际产物。已有代码先看启动方式与项目约定。
2. 将每个关键决定标为已确认、候选或待验证。以用户明确决定和当前权威配置确定规则，以已通过的画面确定视觉。标注由AI补出的布局、文案和数值。
3. 根据实物判断进度。分清文档已写、逻辑已检查、浏览器已运行、真机已操作、真人已试玩。记录各自证据及缺口。
4. 沿用项目阶段编号。选离本轮目标最近的未完成步骤，复用已完成内容。只有目标或证据变化时才返回前一步。
5. 用户只想要提示词、计划或评审时，交付对应内容。用户要求设计或实现时，推进至可查看或可运行的产物。用户明确提出评审停止点时，在该点交付。
6. 开始前用几句话说明本轮目标、主要产物和验证办法。可逆细节采用合理假设并记录。遇到会根本改变方向的缺失信息才问一个聚焦问题。

## 2 定义本轮开工单

压缩成一页或项目现有进度记录中的一节。

| 字段 | 填写要求 |
|---|---|
| 玩家与场景 | 暂定目标玩家、平台、设备、输入方式、一次游玩的时间场景 |
| 玩家体验 | 玩家想成为谁、想完成什么、希望感受到什么 |
| 重复操作 | 写出一轮目标、行动、代价、反馈、下一次选择 |
| 当前疑问 | 只挑本轮最影响后续投入的一两个问题 |
| 验证范围 | 写明起始状态、可做动作、结束条件、重试方式 |
| 实际交付 | 写明要让用户看到或亲手操作的产物 |
| 判断依据 | 写明观察到什么会保留、修改或舍弃方案 |
| 临时假设 | 标注数值、内容数量、场景和技术的试验取值 |

## 3 根据当前疑问选择验证方式

| 当前主要疑问 | 优先动作 | 下一步依据 |
|---|---|---|
| 资源与选择是否有取舍 | 用卡片、表格或小脚本推演一轮，比较两条路线 | 玩家能解释选择的收益与牺牲，规则与成本可复算 |
| 信息是否看得懂、操作是否顺手 | 画少量关键线框，尽快做真实尺寸的可点击原型 | 新玩家能从界面判断目标、代价、可做动作和结果 |
| 动作、镜头、物理或触控手感 | 用目标设备或引擎做最小场景 | 实际输入和反馈达到本轮定义的手感目标 |
| 游戏看起来是否符合期待 | 用一张关键视觉候选，再做可操作HTML样稿或引擎画面 | 制作人能评审布局、风格、信息和关键操作 |
| 平台、性能或联网是否可行 | 用小范围技术试验跑通目标能力 | 留下运行环境、结果和限制 |
| 后续内容能否持续制作 | 做一段接近成品的代表体验，再制作第二份同类内容 | 掌握真实追加成本、复用方式与返工原因 |

将玩法、界面和技术试验交叉推进。对UI承载玩法的项目，把排布、拖拽、切屏、信息显隐一起验证。对动作类项目，按手感问题决定原型工具。

## 4 推进六个制作阶段

### 阶段一 明确目标

完成开工单，圈出最小的一段有意义体验。规划全项目的大致阶段，优先细化即将制作的部分。基于目标平台和设备确认屏幕方向、操作方式和已知约束。

### 阶段二 验证核心玩法

先用最低成本让人做一次真正选择。让AI自行演算可行路线、失败路线和边界，随后交给人操作或决策。

数值验证应明确评价目标、输入范围、前提、单位和算法。只在实际检查范围内报告最优或可行。只有新增机制确实回答原有设计问题时才引入它。每轮追调开始前写明要解决的一个问题和结束条件，完成后进入试玩。

保留同一套权威配置。结果发生变化时，检查输入、公式、单位和可行性条件，解释变化来源。将玩家是否愿意重试、是否感到选择有用交给真人试玩观察。

### 阶段三 做可玩的HTML或引擎原型

从实际玩家行动推导界面。写清行动前要知道什么、点击哪里、行动代价、系统反馈和下一步。先接通起点、操作、结果和重试，再扩充内容。

复用项目已有技术。缺少现有工程时，根据本轮问题选择容易运行和修改的技术。界面为主的HTML样稿可用原生HTML、CSS与JavaScript。存在重物理、复杂3D或特定平台交互要求时优先做对应技术试验。

当用户要求“用HTML把我们想做的样子设计好”，交付可操作的视觉样稿，覆盖布局、信息层级、代表性美术、按钮状态和连续流程。根据已有灰度稿继续提高表现质量。使用真实界面元素绘制动态文字、价格、数量、按钮和格子。

集中维护规则配置与本局状态。让时间、资金、库存和选中角色随同一局连续变化。把页面、选中项、拖影等临时UI状态单独处理。复用商品、物品实例和位置数据，为未来扩展保留已知输入输出。

### 阶段四 观察玩家并修正

给目标玩家可理解的任务，尽量让界面承担解释。记录玩家看到了什么、做了什么、当时想达到什么、产生什么后果，再用中性问题追问。

| 观察 | 优先修改 |
|---|---|
| 找不到入口、误解代价或不知道为何失败 | 信息层级、文案和反馈 |
| 知道要做什么但放不准、点不中或被遮挡 | 触控、布局和操作反馈 |
| 看懂后觉得取舍无意义 | 规则、资源价值和后果 |
| 想继续但重复操作令人疲惫 | 操作频率、节奏与快捷方式 |
| 不同界面显示同一局的不同余额或库存 | 状态来源、结算顺序与恢复逻辑 |

每次优先改最影响目标的一处，再用同类任务验证。记录样本与测试条件。将少量试玩作为方向证据，继续观察后续体验。

### 阶段五 制作接近成品的代表片段

选一段能代表游戏的完整体验，贯通视觉、规则、声音、交互、状态恢复、资源导入、打包和目标设备运行。提炼字号、间距、色彩、按钮、卡片、弹窗、图标与素材规格。

用户已选择先完成HTML设计时，沿HTML样稿迭代到约定评审点，再进入引擎复现。具体引擎、版本与平台SDK沿用项目决定，实施前核对当前官方文档和本地能力。

将第二个真实场景做出来，检验复用是否有效。记录增加一间商店、一个角色或一段事件所需的配置、美术、代码和验收工作。用这些成本调整首版范围。

### 阶段六 扩成可测试首版

按已验证循环与实际产能排功能和内容。每批形成能玩的版本，覆盖引导、自由操作、成功、失败、存读和重试等适用路径。引入统计时记录与当前问题直接相关的开始、选择、失败原因和完成结果。

在计划对外发布前核对目标平台构建与分发要求、对应账号能力和已选商业化方案。具体接入安排服从项目需求。以试玩发现、运行故障和完成情况决定下一轮。

## 5 做好HTML视觉与交互

- 先读已有风格稿。找不到原图时，将新绘制图片标为候选，记录所依据的风格描述。
- 从玩家当前处境和核心行动设计首页，给最重要的决定更清楚的位置。根据游戏需要使用场景、角色和物品表现。
- 为每个操作覆盖必要的正常、可执行、不可执行、进行中、成功与失败状态。给出具体原因和恢复办法。
- 按目标设备设计。手机检查文字、触控尺寸、安全区、手指遮挡和短屏内容，桌面检查鼠标、键盘和窗口缩放。拖拽同时提供可行的点选替代。
- 格子或容器玩法核对真实几何、所有权和提交时机。购买、待装、布局草稿、最终携带、留货各有明确状态。预览可撤回，确认产生明确后果。
- 让同一配置驱动预估与实际结算。操作失败保持业务状态一致，连点与恢复时保证一次提交只发生一次。
- 让文字和图标在深浅背景上都可读。使用细节动效帮助理解选择、移动和确认，按设备能力控制资源成本。
- 交付明确的打开方式。独立离线HTML嵌入必要资源，项目型原型提供准确入口与启动方法。结束时指出本轮最值得查看的两个画面或操作。

## 6 运行与验收

先运行已有检查，再验证本轮新增或受影响的路径。关键问题补最小的回归检查。

1. 检查配置单位、计算公式和预期账目。
2. 在可用浏览器或引擎中打开实际交付物，检查控制台和页面状态。
3. 走通正常、取消、失败恢复、重复确认和再次开始等相关路径。需要保存时验证退出重入。
4. 在目标视口查看截图，检查遮挡、截断、横向溢出和信息密度。
5. 需要触控或设备特性时记录真机测试。对玩法理解和趣味性记录真人试玩。
6. 环境限制导致某项未执行时，记录具体未验证部分。将代码检查、模拟DOM、浏览器操作、真机操作和真人试玩分别报告。

## 7 和人与其他Agent交接

由人决定体验目标、关键取舍和是否扩大投入。让AI负责检索依据、提出可比较方案、实现、演算、运行、修正和整理证据。对独立工作可并行委派，明确各自输入、输出、文件范围和最终整合者。

每个任务使用以下结构。

> 读取哪些项目材料。沿用哪些已确认规则。解决本轮哪个问题。实现哪一段体验。允许哪些临时假设。交付什么可查看或可运行产物。怎样验证完成。

沿用项目已有进度入口，记录本轮实际产物、权威配置、已通过决定、未验证事项和下一步。将版本关联到对应代码或文件。依赖确认时先交付足够评审的结果，已授权的实现任务持续推进到本轮完成条件。

最终交付简短包含可打开的入口、本轮主要变化、已做检查、临时决定、未验证项和下一步。用户能仅凭最终回复接续工作。

## 8 末世房车迁移示例

以项目实际最新材料为准，读取策划案、阶段进度、配置、线框、视觉参考和HTML。用户已完成玩法推演且想提高HTML表现时，从连续界面与视觉样稿接手。

可截取“营地→地图→采购→回车装载→明确留货→爆发准备结果”。用同一局状态贯穿每屏，用实际采购和摆放结果生成清单。初始资金、车型、货物尺寸和耗时从本项目配置读取。原型起点与结果范围写明，死亡回溯与灾后玩法按当前制作范围衔接。

将该例中的商店、车辆和库存替换为其他项目自己的核心动作。重新选择最需要验证的问题和适合它的工具。

## 9 方法依据

按当前任务选择性阅读相关案例，应用其中适合项目的做法。

- Lucas Pope 的《Papers, Please》开发日志记录了原型操作如何改变证件界面布局。[开发日志](https://dukope.com/devlogs/papers-please/tig-00/)
- Rami Ismail 讨论了原型、垂直切片和第二份内容在验证玩法与产能中的作用。[制作方法](https://ltpf.ramiismail.com/prototypes-and-vertical-slice/)
- 《纪元》制作团队说明了设计评审、占位素材可玩、里程碑试玩与计划调整。[制作团队访谈](https://www.anno-union.com/devblog-planning-anno-the-production-department/)
- Steve Bromley 说明了从预期玩家行为设计任务、观察操作与中性追问的方法。[试玩方法](https://gamesuserresearch.com/find-usability-issues-in-games-with-playtests/)
