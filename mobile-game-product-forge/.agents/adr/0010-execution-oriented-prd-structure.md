# ADR-0010：PRD 使用统一研发执行结构

- 状态：已采纳
- 日期：2026-07-26
- 影响：PRD 公共格式契约与校验（中等迁移成本）

## 背景

原 20 章结构偏审计完备，同一条规则分散在目标、场景、客户端、服务端、状态、异常和验收等多章，研发需要跨章拼接信息；章节裁剪本身也产生额外维护成本。按技术模块拆章又会让 AI 把客户端、服务端、数据库、配置和埋点拆得过细。

## 决策

新 PRD 改为统一 7 章研发执行结构，并通过条件触发专项承载配置、埋点、第三方、状态机、迁移和上线内容。

多模块需求默认只记录影响范围，正文仍按总体流程和业务规则组织。只有存在独立业务闭环时，才允许在功能规则内部按业务能力分组；客户端、服务端、数据库、配置和埋点不得作为功能模块拆章。

项目不设运营后台章节，运营控制统一写配置表合同。图形按要解决的问题选择，不机械生成。

历史 20 章 PRD 继续兼容，不强制迁移。

## 备选方案

- **保留 20 章，仅增加裁剪规则**：仍需维护章节清单和省略原因，不能解决信息分散。被否。
- **按技术模块拆章**：容易产生重复规则和过细模块，AI 难以稳定控制。被否。
- **每个业务模块独立 PRD**：对普通需求过重，只适合真正可独立开发和验收的业务闭环。被否。

## 后果

- 新 PRD 更短，客户端、服务端和测试围绕同一 `R-###` 理解职责与结果。
- L1/L2/L3 共用结构，只改变深度；无需章节裁剪决定。
- `lint-prd.py` 同时识别规则/验收表格和历史结构。
- 结构精简不能削弱 D-### → R-### → AC-###、配置合同、数据权威、异常恢复、第三方适用证据和原型确认/豁免。
