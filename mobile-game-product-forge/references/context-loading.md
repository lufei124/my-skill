## 1. 目标与能力保真

本合同是根编排器、需求发现、原型、PRD 写作和 PRD 评审共享的唯一上下文加载规则。优化目标是减少重复读取和无关上下文，不是限制调查能力。

优先级固定为：

```text
事实正确性
> 信息完整性
> 业务与评审能力
> 当前状态和目标状态区分
> 多 Agent 一致性
> 用户操作流畅度
> 响应速度
> Token 消耗
```

必须遵守：

- 上下文优化不得降低事实完整性、业务正确性、原型保真或评审覆盖。
- 摘要、快照和角色切片都不是业务权威源；证据不足时必须读取原始材料。
- 来源冲突、高风险或无法确认是否遗漏时，自动扩大读取，不新增用户确认。
- 上下文预算是软预算，不得作为停止读取必要证据的理由。
- 默认少读，但不能少查：先用摘要和索引定位，再用权威原文验证。
- 当前实际状态、历史设计和目标状态必须明确区分。
- 历史 PRD 或知识内容不得直接当作当前线上事实；当前代码实现不得直接当作目标产品规则。

## 2. 三类权威来源模型

不得用一条线性优先级同时裁决产品目标、当前线上现状和外部约束。

### 产品目标与决策权威

用于判断“这次最终要做成什么”：

```text
用户最新明确确认
> 当前有效且已确认的需求摘要与决策账本
> 当前已确认原型中的交互决策
> 当前已通过评审的 PRD 规则
> 未确认方案
> AI 推断
```

时间更晚且被明确确认的决定可以取代旧决定，但必须在决策账本、摘要、原型和 PRD 中记录替代关系及待同步范围。上述已确认产物互相冲突时不得静默按顺序覆盖；AI 推断不得覆盖任何已确认决策。

### 当前现状证据

用于判断“产品现在实际上是什么”：

```text
当前线上行为、当前代码实现、正式配置、当前接口或数据库状态
> 当前有效的项目现状文档
> 当前设计稿、测试环境和后台实际能力
> 历史 PRD、历史文档和历史配置
> 用户记忆或口述
> AI 推断
```

证据强度不等于目标规则正确性。线上行为可能是缺陷或临时逻辑，代码可能偏离产品目标，知识库可能过期，用户口述可能不完整。每项现状证据必须记录时间、版本、环境和适用范围。

### 外部约束权威

用于判断平台、合规和第三方要求。权威性必须与适用性一起判断，不能只按“发布时间最新”排序：

```text
适用于目标地区和目标发布日期的官方政策、合规要求与正式协议
> 与当前接入版本或已确认目标升级版本匹配的官方 SDK / API 文档
> 源版本 + 目标版本 + 官方迁移指南、发布说明和弃用时间表
> 项目内部技术说明与实际接入证据
> 第三方文章、社区讨论和经验
> AI 记忆
```

执行规则：

- 平台政策与合规：使用适用于目标地区、目标渠道和目标发布日期的最新官方规则。
- SDK、API 与技术行为：使用与当前接入版本匹配的官方文档；若需求已确认升级目标，则同时使用目标版本文档。
- 版本迁移：同时核查源版本、目标版本、官方迁移指南、弃用时间和兼容限制，不能用目标版本接口反推当前版本能力。
- 每项外部结论记录官方来源、访问日期、适用地区/渠道、当前版本、目标版本和适用性判断；无法匹配时标“待确认”，不得用 AI 记忆补全。

`context-snapshot.md`、角色切片和 AI 摘要不属于以上任何一类权威源，只是证据导航。

## 3. 冲突处理：当前状态、目标状态与改动

发现来源冲突时不得只选择“更高优先级”后继续。输出：

```text
冲突主题：
来源 A：
来源 B：
各自版本或时间：
当前现状：
目标状态：
可能原因：
影响范围：
需要谁确认：
建议处理：
```

必须明确区分当前状态、目标状态、从当前状态到目标状态的改动。若冲突只影响现状判断，先扩大实现和数据核验；若影响目标产品方案，集中交由产品负责人确认并同步受影响产物。

## 4. 需求调研来源与现状核验

需求调研通过六类来源建立可信现状、目标、冲突、未知项和风险：

1. **用户访谈**：为什么做、谁遇到问题、当前痛点、成功目标、本期/非本期范围、确认/未确认决策、时间和资源限制。
2. **项目知识**：项目背景、模块现状、业务规则、配置、技术约束、数据口径、UI、术语、当前有效 PRD 和历史决策索引。逐项标记「当前有效 / 可能过期 / 历史参考 / 存在冲突」。
3. **当前实现核验**：按影响范围核查实际页面与交互、客户端/服务端逻辑、正式配置、API、数据库字段与状态、埋点、后台、已上线版本、测试环境和现有设计稿。始终分开记录文档描述、实际实现和目标设计。
4. **历史证据**：历史 PRD、ADR、决策账本、Git 变更、历史评审、旧原型、事故修复、已关闭问题和需求变更。只在现状难解释、来源冲突、准备推翻旧规则、高风险、审计追溯或用户要求时读取。
5. **数据和用户反馈**：涉及增长、留存、商业化、体验优化或问题修复时，按需核查埋点、漏斗、留存、转化、实验、错误日志、客服、商店评论、用户、运营和测试反馈。没有量化证据时明确写「当前缺少量化证据」，不得把主观判断写成数据结论。
6. **外部调研**：海外习惯、竞品交互、平台规则、支付订阅退款、广告归因、第三方 SDK、隐私合规、国家/语言/渠道差异、新商业化或内部无成熟方案时触发。政策/合规按目标地区与发布日期匹配，SDK/API 按当前或已确认目标版本匹配，升级同时读取源版本、目标版本和官方迁移指南。普通文案和简单配置不机械执行。

## 5. L1/L2/L3 调研深度

- **L1**：至少用户输入 + 当前模块规则 + 当前实际配置或实现核验；按需补当前页面、相关埋点和一名相关角色意见。不默认读全部历史或外部资料，但仍须生成精简 `00-research-findings.md`，至少记录用户目标、当前规则、当前配置或实现核验、当前状态、目标状态、差异、风险和来源。
- **L2**：通常包含用户访谈 + 项目知识 + 当前实现 + 相关数据/反馈 + 必要历史证据 + 相关角色事实输入；涉及外部平台时补官方资料。
- **L3**：必须完整核验当前实现、历史决策、数据/反馈、技术约束、平台/合规、多角色事实输入、异常/补偿/兼容/迁移，以及当前状态与目标状态差异。L3 不受上下文软预算限制。

所有正式需求都必须形成调研产物；复杂度只改变调研深度，不允许跳过 `projectContext.status=completed`。新格式 `00-research-findings.md` 至少必须为非空文件，并保留模板中的「当前现状、目标状态、当前状态与目标状态差异、风险、来源索引」五个稳定标题；旧 `00-project-context.md` 仅作兼容，但也不得为空。最低结构只防止空文件或残缺模板冒充已完成调研，具体证据质量仍由需求发现 Skill 与协调 Agent负责。调研完成不是新的用户确认门。需求发现 Skill 写出产物并返回后，由协调 Agent 把相对路径、非空版本和完成状态写入现有 `projectContext`。

## 6. 根编排器默认读取顺序

每轮先定位，不先全量读取：

1. `00-stage-state.json`；
2. 状态中当前阶段记录的当前文件；
3. 当前 `context-snapshot.md`（存在时）；
4. 当前阶段必要的共享合同和子 Skill；
5. 执行证据完整性检查，再决定是否读取第二层或第三层证据。

根编排器不得默认读取 README、完整操作指南、全部 `references/`、全部子 Skill、完整需求目录、全部历史 PRD、全部历史原型或全部评审报告。仅当用户询问如何开始、继续、查看流程、使用 Skill，或 setup 需要告知入口时读取操作指南。

## 7. 三层渐进式加载

### 第一层：默认上下文

所有阶段先读取状态、当前快照、当前阶段核心产物和当前 Skill 核心规则。

- PRD：状态、目标为 `prd` 的快照、当前决策账本、`prototype-meta` 或正式豁免、PRD 规范。
- 评审：状态、冻结的 review 快照、当前 PRD、当前角色规则。
- 原型与需求发现的具体默认输入由对应子 Skill 声明。

第一层用于定位，不得因为已读快照就假定证据完整。

### 第二层：相关证据

出现信息缺口时，按证据索引读取直接相关片段：

- 对应 `D-###`、需求摘要章节；
- 对应原型页面、场景、状态或 DOM 片段；
- 对应 PRD 章节、`R-###`、`AC-###`；
- 对应项目知识模块；
- 对应配置、字段、接口或埋点定义。

优先定位文件和章节，不把无关原文带入上下文。

### 第三层：完整或扩展原文

任一触发器成立时必须扩大读取：

- 快照无法给当前结论提供权威来源；
- 来源之间冲突，或当前版本与历史决策疑似冲突；
- `prototype-meta` 缺失、不完整或与页面疑似不一致；
- `D-###`、`R-###`、`AC-###` 关系不一致；
- 多个评审角色对同一事实或规则理解矛盾；
- 用户质疑结论、要求追溯或比较历史版本；
- Agent 对事实没有足够把握；
- 当前材料不能支持明确验收标准；
- 当前输出可能造成严重线上风险；
- 命中「高风险主动深读」范围。

扩大顺序仍是先相关片段，再相关文件，必要时才读完整原文或历史集合。

## 8. context-snapshot 定位与冻结

每个正式需求可维护：

```text
history/<日期>-<需求简称>/context-snapshot.md
```

它是从 `00-research-findings.md`、确认摘要、决策账本、确认原型/豁免和当前 PRD 中提取的“目标阶段摘要 + 原始证据索引 + 来源版本记录”，不是调研记录、状态源、业务权威源、确认门或长期缓存。用户不需要手工创建或维护。

生成与冻结：

1. 需求发现 Skill 在需求理解确认前完成 `00-research-findings.md` 和摘要草稿，不生成阶段快照。
2. 需求摘要已确认且原型确认或豁免证据就绪后，协调 Agent 生成或更新目标为 `prd` 的快照。
3. 当前 PRD 进入评审前，把 PRD 版本和受影响章节写入快照，冻结目标为 `review` 的版本。
4. 并行角色使用同一冻结快照和同一 PRD 版本；评审期间不得让单个角色改写公共核心。
5. 来源冲突或权威来源变化时，更新受影响部分并提升快照版本；旧快照不作为当前事实继续分发。

模板与字段见 [templates.md](templates.md)「当前阶段上下文快照」。

## 9. 来源版本、指纹与增量更新

快照为每项来源记录文件、业务版本、内容指纹或更新时间和当前状态。

- 来源全部未变化：复用快照，不重读或重建。
- 仅决策账本变化：更新决策、规则、范围和受影响风险。
- 仅原型变化：更新页面、场景、状态、交互和相关决策。
- 仅 PRD 变化：更新评审目标版本、受影响章节及 `R/AC` 索引。
- 项目知识变化：只重核受影响模块。

指纹只用于发现来源变化，不能证明内容正确。快照过期判断由协调 Agent 自动执行，不新增用户确认。

## 10. 当前版本与历史版本

默认只读取状态和快照指向的当前有效版本。不默认读取旧 PRD、已替代原型、历史评审报告、已替代需求摘要、已关闭决策或完整需求目录。

仅在用户要求对比、决策追溯、疑似历史冲突、范围变化未记录、生成变更说明、审计/事故追踪或当前版本缺少必要来源时读取历史。历史读取先定位具体文件和章节，不默认加载全部历史。

## 11. prototype-meta 完整性与 HTML 降级

本节是 metadata 字段与降级行为的唯一共享合同；其他 Skill 只引用本节，不另建字段或枚举词表。机器支持版本和枚举集中定义在 `scripts/check-stage-gate.py`，当前正式模板使用 Schema `1.0`。

本合同只适用于 `prototype.applicability=required`。`not_applicable + waived` 路径不要求 `index.html`、metadata、页面/场景/状态或 HTML 回读，只校验调研、需求摘要和豁免证据。

required 路径进入 PRD 或评审前运行 `--extract-prototype-meta`：

- `COMPLETE`（退出码 0）：metadata 存在、JSON 根节点为 object、必需字段/类型/枚举/内部结构有效、ID 不重复，Confirmed 原型至少含一个页面、一个主场景和一个状态，且真实业务字段不得仍是模板占位值；输出紧凑 metadata，可作为第一层输入。
- `INCOMPLETE`（退出码 2）：JSON 合法但业务字段不足，输出 `missingFields`、`invalidFields`、`duplicateIds` 与 `nextAction=read_relevant_html`。字段缺失、类型或枚举错误、内部对象不完整、ID 重复、非法 `D-###`、Confirmed 缺页面/场景和历史最小 metadata 均归此类。
- `INVALID`（退出码 3）：metadata 容器缺失/为空、JSON 无法解析或根节点不是 object。

### 字段与语义

- 顶层必需：`schemaVersion`、`requirementName`、`module`、`prototypeVersion`、`prototypeStatus`、`device`、`scope`、`pages`、`scenarios`、`states`、`decisions`。
- `schemaVersion`：非空 string，且属于脚本集中声明的支持版本。
- `requirementName`、`module`：非空 string。
- `prototypeVersion`：非空 string，使用现有 `v数字.数字` 版本形式。
- `prototypeStatus`：只允许 `Draft` / `Confirmed`。
- `device`：object；`orientation` 只允许 `portrait` / `landscape`；`platform` 为非空 string 数组。
- `scope.included`、`scope.excluded`：必须显式存在且为 string 数组；元素不得为空或只有空白。
- `pages`：object 数组，每项含非空 `id` / `name`；ID 不重复。Confirmed 时不得为空。
- `scenarios`：object 数组，每项含非空 `id` / `entry`，并以 `flow` 或 `result` 表达流程/结果；`flow` 为非空 string 数组，ID 不重复。Confirmed 时不得为空。
- `states`：object 数组，每项含非空 `id` / `description`，ID 不重复；Confirmed 时至少记录一个默认或业务状态。
- `decisions`：显式数组，可以为空；非空时每项含合法 `D-###` `id`、非空 `summary`，状态只允许决策账本现有词表「待确认 / 已确认 / 已排除 / 已替代」，ID 不重复。
- Confirmed 状态下，`requirementName`、`module`、平台、scope、页面 ID/名称、场景 ID/入口/流程或结果、状态 ID/说明、决策摘要中的真实业务值不得使用精确占位值「待补充 / 待确认 / TODO / TBD / PLACEHOLDER / 示例」。`decisions[].status=待确认` 仍是合法决策状态，不受占位值规则影响。

### required 历史兼容

历史原型不批量迁移，但历史最小 metadata 不得直接通过 PRD 门禁。required 路径遇到 `INCOMPLETE` 或 `INVALID` 时，消费 Skill 必须先按字段清单定向读取相关 DOM、内嵌数据或交互脚本；证据不足时扩大到相关 HTML，最后才读取完整 HTML。根据实际证据补齐 metadata、标记历史兼容核验并重新分类，只有 `COMPLETE` 且 `prototypeStatus=Confirmed`、版本与状态文件一致后才能进入正式 PRD。

若 HTML 仍无法支持缺失字段，不得伪造 metadata；输出证据缺口并返回原型阶段，由产品负责人或原型负责人补充。默认不读完整 HTML、软预算或历史兼容都不能成为跳过核验的理由。

metadata 与页面疑似不一致、需要核对具体文案/按钮/弹窗/关闭/返回/二次确认/反馈、用户明确要求核对实际原型或高风险交互只存在于 HTML 逻辑时，即使分类为 COMPLETE 也应按同样顺序定向回读。机械提取优先复用 `scripts/check-stage-gate.py --extract-prototype-meta`，其输出不得包含 HTML、CSS 或 JavaScript。

## 12. 高风险主动深读

支付、订阅、订单、账号、登录、数据迁移、资产和奖励、广告奖励、商业化价格、隐私和合规、服务端补偿、幂等、跨端状态同步、大规模配置迁移不得只依赖快照。

至少主动核查：

- 权威决策和当前 PRD 规则；
- 原型或豁免依据；
- 客户端/服务端职责；
- 异常、幂等、补偿和恢复；
- 对应验收标准。

高风险场景允许并要求超过软预算。

## 13. 多角色共享核心与专业增量

所有评审角色必须收到同一公共业务核心：

- 用户目标、本期范围、主流程、核心规则；
- 关键状态、关键异常、当前风险；
- 当前快照和 PRD 版本。

在公共核心上追加专业增量：

- 产品/交互：页面、场景、状态、反馈、metadata、体验和范围一致性。
- 客户端/服务端：端职责、数据流、接口、配置、状态一致性、异常、兼容、幂等。
- 数据：成功指标、流程节点、埋点、属性、指标口径、漏斗、实验。
- 测试：规则、页面状态、异常、边界、验收、配置组合、兼容。
- 运营/商业化：用户分层、配置、商业规则、价格奖励、国家渠道、活动和维护成本。

不得让每个角色重新读取整个项目、完整 HTML、全部历史或其他角色的完整规范，也不得把公共业务背景完全隔离。

## 14. 角色切片、版本一致性与冲突汇总

默认不创建永久角色切片。只有 PRD 很长、角色只需少量章节、并行平台无法精确传递片段、上下文明显过大或 L3 跨模块较多时，才生成临时切片。

临时切片必须来自同一冻结快照和当前 PRD，保留公共业务核心，不新增事实、不改变 `D/R/AC`、不成为权威文档、不默认长期保留。

角色返回问题列表后，协调 Agent 只读取冻结快照、当前 PRD 和各角色问题列表做冲突汇总，检查：

- 每个角色是否记录 `reviewRole`、`snapshotVersion`、`prdVersion`、`prototypeVersion`、`reviewedAt`；
- 所有角色是否使用相同 `snapshotVersion` 和 `prdVersion`；
- required 路径的相关角色是否使用相同 `prototypeVersion`；
- 评审期间输入是否被修改，是否有角色使用旧版本；
- 数据方案是否支持产品目标；
- 客户端交互是否有服务端状态支撑；
- 测试验收是否覆盖核心商业规则；
- 各角色是否引用同一快照和 PRD 版本；
- 同一规则是否存在矛盾理解；
- 是否需要扩大证据读取、返回原型或返回需求阶段。

版本不一致时不得直接汇总为 `passed`。协调 Agent 向过期角色提供当前输入，只重审受影响部分，并记录不一致原因；无需增加状态字段。事实冲突按「三层渐进式加载」扩大证据读取。

## 15. L1/L2/L3 上下文软预算

软预算用于发现异常读取，不是硬限制：

- L1：默认 3–4 个核心业务文件，快照约 800–1500 中文字符，1–2 个直接专业角色，默认不读完整 HTML 和历史版本。
- L2：默认 5–7 个核心业务文件，快照约 1500–3000 中文字符，多角色复用快照，HTML 和历史按需读取，必要时临时切片。
- L3：PRD 和评审前必须有证据索引快照，快照约 3000–6000 中文字符且必要时可超过；高风险主动深读，跨模块冲突时扩大历史读取。

超出软预算时依次删除无关规范、旧版本，使用 metadata、快照和专业切片；仍不足时继续读取必要原文。不增加任何 token 状态字段、审批或精确计费机制。文件数量只作软参考，绝不因超出参考值中止必要证据读取。

## 16. 校验时机与并行

- 编辑过程中：只运行与当前修改相关的 metadata、链接、状态门禁或 PRD lint。
- 阶段完成：运行阶段门禁、PRD lint 及当前阶段相关检查。
- 仓库维护或最终发布结束：运行完整 `validate.sh`、文档影响检查和架构检查。

最终验证覆盖不得削弱。

客户端、服务端、测试、数据、运营/商业化评审可以在冻结同一快照和 PRD、明确角色任务且禁止修改共享输入后并行。需求确认与原型生成、原型确认与 PRD 生成、依赖未完成的 PRD 写作、评审争议裁定与受影响原型重做不得并行。

## 17. 轻量能力回归场景

每次修改上下文加载规则至少人工或自动核对：

- L1 配置/文案/埋点：避免完整原型和历史版本读取，仍产出完整验收。
- L2 商城/活动/页面：metadata 足够时不读完整 HTML，原型/PRD 保真不下降，多角色复用同一快照。
- L3 支付/订阅/核心玩法：主动深读高风险证据，保持完整评审覆盖，发现跨角色冲突，不为节省上下文跳过必要材料。
- 用户、知识和当前配置分别写 1/3/2 次：不静默选择，分别写当前状态与目标待确认项。
- 历史 PRD 与线上实现不同：历史只作历史证据，线上实现只作当前状态，不把当前缺陷自动当目标规则。
- metadata 合法但不完整：返回 `INCOMPLETE` 并回读相关 HTML，不遗漏页面、状态和交互。
- 多角色使用不同快照版本：不得进入 `passed`，只重跑过期角色。

质量指标优先：核心规则遗漏、`D/R/AC` 映射错误、原型/PRD 漂移和评审问题遗漏不得增加，用户确认往返不得增加。效率指标用于比较重复文件读取、完整 HTML/历史读取次数、输入规模、多 Agent 重复上下文和执行时间；质量下降时回退对应优化。
