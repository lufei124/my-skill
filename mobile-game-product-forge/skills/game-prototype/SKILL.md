# 游戏交互原型

针对**单次需求**生成的一次性、模块级、可点击交互原型，用于确认用户路径、页面状态、业务决策和异常处理；确认后作为 PRD 的权威输入之一，不作为长期前端资产维护。

本子 Skill 是 `mobile-game-product-forge` 的能力拆分。需求处理模式、确认门、版本号和共享工作目录由编排器持有；正式编排时本子 Skill 只读阶段状态并验证门禁，不修改跨阶段状态。

## 前置条件

1. 正式需求调研状态=`completed`，调研文件为当前需求目录内的 `00-research-findings.md`（历史兼容 `00-project-context.md`），文件存在且版本非空。
2. 需求摘要状态=已确认（需求理解确认门已通过，存在已冻结的《需求理解与方案摘要》，即 `01-requirement-summary.md`，历史需求兼容 `01-requirement-decisions.md` 承载）。
3. `prototype.applicability=required`。有新页面、入口、主路径、按钮、弹窗、状态反馈或交互变化时必须为 required；无 UI/交互变化且产品负责人已确认豁免时，本 Skill 不执行，由根编排器记录 `not_applicable + waived`。
4. 编排器已读取项目知识库中的 UI 规范和历史组件（模式1/模式2）。
5. 作为窄任务独立调用时的最小输入：要原型的功能范围与设备/朝向要求；缺失则只问这一个问题，不生成原型。
6. 消费边界：以已确认《需求理解与方案摘要》与决策账本为权威，不重新访谈、不重新推导上游已确认决策；上游缺口标待确认项交回，不自行假设填充。
7. 版本一致性核对：核对《需求理解与方案摘要》版本与决策账本（`01-requirement-decisions.md`）一致；不一致先回 `game-requirement-discovery` 重冻摘要，不按过期摘要返工原型。

## 正式流程门禁

正式编排调用时，生成或迭代原型前必须读取工作目录 `00-stage-state.json`，并按 [阶段状态与硬门禁](../../references/stage-gates.md) 执行 `check-stage-gate.py --target prototype`。退出码非 0 时只输出门禁结果、缺失条件和返回阶段，不生成 HTML。

用户明确“只做原型”时可作为 `narrow_task` 独立调用，但产物必须标注完整流程门禁未执行，不修改 `00-stage-state.json`，也不自行进入 PRD。原型豁免不是窄任务，Agent 不得自行批准。

## 输入

- `00-research-findings.md`（历史需求可用旧 `00-project-context.md`）
- 需求摘要与已确认决策（决策账本 `D-###`）
- 历史 UI、截图、视觉规范和可复用组件
- 设备要求

## 上下文加载

默认读取：`00-stage-state.json`、当前已确认需求摘要、当前决策账本、调研结论中的当前/目标状态差异、与当前模块直接相关的 UI 规范/组件索引和用户提供的当前素材。原型前通常还没有 `context-snapshot.md`，不得把它当作必需输入。

不默认读取：整个项目知识库、完整需求目录、旧 PRD、已替代原型或无关模块 UI。摘要与账本不一致、当前素材缺少交互依据、历史 UI 疑似冲突、用户要求追溯或命中支付/账号/资产/商业化等高风险交互时，按 [上下文加载合同](../../references/context-loading.md)「快速执行索引」中「原型」行的默认与触发扩展章节读取相关原文，必要时扩大范围。软预算不得阻止原型保真核查。

## 1. 适用范围

原型只服务于当前需求，不承担正式开发，也不跨需求复用。多名产品经理分别负责不同模块时：

- 每个需求独立生成自己的原型；
- 不依赖其他产品经理的原型工程，不合并成完整游戏；
- 只生成当前模块和理解当前交互所必需的最小入口上下文；
- 不为展示入口而重建完整首页、完整游戏或无关模块。

例如需求是 VIP 订阅页，只生成：理解入口来源的最小上下文、VIP 页面、购买确认、购买成功/失败与相关异常；不为展示 VIP 入口重建整个商城、首页、角色系统或支付后台。

## 2. 默认交付形式

默认产物：

```text
02-prototype/
└── index.html
```

`index.html` 必须：HTML/CSS/JavaScript 全部内嵌；双击或浏览器直接打开即可运行；无需 `npm install`、无需本地服务器、不依赖后端、真实账号、真实 SDK 或易失效 CDN；不把外部图片能否加载作为主流程可用的前提；不修改正式项目代码。

只有用户明确要求，或现有项目存在明确且必须遵循的原型技术栈时，才允许改用其他形式（React/Vue/工程脚手架等）。默认不引入公共组件库、跨模块原型工程、npm 流程、正式路由、Design Token 系统、状态机框架、真实接口/支付/广告 SDK、自动化测试或截图脚本。

## 3. 优先验证产品逻辑

优先级：

```text
交互与业务逻辑正确
> 主流程和异常完整
> 页面信息层级清晰
> 视觉接近项目
> 装饰性和展示效果
```

不得为视觉效果牺牲流程完整性。原型必须重点表达：用户从哪进入、页面解决什么任务、可执行哪些操作、点击后发生什么、如何返回/关闭、成功后页面如何变化、失败如何处理、条件不满足如何反馈、重复点击如何处理、重新进入展示什么、哪些规则已确认、哪些问题待确认。

## 4. 只覆盖实际相关状态

只实现与当前需求、已确认摘要和已确认决策实际相关的状态，不得为形式完整机械加入无业务意义的状态。按需从以下选择：默认、首次进入、正常、Loading、成功、失败、空、禁用、条件不足、次数达上限、权限不足、网络异常、配置失效、重复点击、中途关闭、切后台恢复、重新进入、已完成/已领取、已购买/已订阅、过期/失效。

## 5. 轻量评审工具栏

单文件 HTML 提供可收起的评审工具栏，不遮挡主要操作区，至少含：当前原型版本、当前场景、当前页面/状态、场景切换、状态切换、重置原型、显示/隐藏产品标注、查看本次范围、查看待确认问题。状态切换用于快速查看异常状态，不必通过复杂操作重复触发。

工具栏只用于原型评审，不属于正式游戏页面，不得写入 PRD 的正式 UI 要求。工具栏的状态项必须来自当前需求实际需要，不固定塞入一整套无关状态。

## 6. 主流程必须可点击走通

不得只生成静态页面或只有按钮样式的视觉稿。至少一条完整主流程从入口走到结果，例如：进入模块 -> 查看页面 -> 点击核心操作 -> 出现确认/Loading -> 成功或失败 -> 页面状态更新 -> 可返回/关闭/重新操作。核心按钮必须具备真实模拟反馈（页面跳转、弹窗开/关、Loading、Toast、成功结果、失败反馈、禁用反馈、次数或状态变化），不得出现大量点击无响应的伪按钮。

## 7. 本次范围与非范围

原型中必须可查看「本次包含」与「本次不包含」范围，按当前需求生成、不直接复制固定示例。评审者应能快速区分：本期已设计内容、仅用于演示的模拟内容、明确不在本期范围的内容、尚未确认的内容。

## 8. 决策引用编号（不提前创建 R-###）

原型阶段不生成正式 `R-###`（PRD 规则编号）。产品标注遵循：

- 已存在于决策账本的决定，引用对应 `D-###` 并标注其状态（待确认 / 已确认 / 已排除 / 已替代）；
- 待确认问题统一引用 `D-###` 并标状态「待确认」；
- 不在原型阶段生成 `R-###`，`R-###` 只在 PRD 阶段生成；
- 只有状态为「已确认」的 `D-###` 才能在 PRD 映射为正式 `R-###`；
- 状态为「待确认」的 `D-###` 写入 PRD 的待确认问题，不生成 `R-###`。

页面标注示例：

```text
[D-003][已确认] 每日最多领取 3 次
[D-006][已确认] 中途关闭广告不发放奖励
[D-008][待确认] 奖励发放失败后是否自动补发
```

不得自行创造不存在的 `D-###`；发现需新增决策时交回协调 Agent 更新决策账本，再回原型。

## 9. 内嵌结构化原型信息（必需合同）

新生成原型必须在 `index.html` 内嵌结构化元数据，作为 PRD Agent 读取确认原型的权威入口：

```html
<script id="prototype-meta" type="application/json">
{
  "schemaVersion": "1.0",
  "requirementName": "待补充",
  "module": "待补充",
  "prototypeVersion": "v0.1",
  "prototypeStatus": "Draft",
  "createdBy": "待补充",
  "createdAt": "待补充",
  "device": {
    "model": "iPhone 16",
    "width": 393,
    "height": 852,
    "orientation": "portrait",
    "platform": ["iOS", "Android"]
  },
  "scope": {
    "included": [],
    "excluded": []
  },
  "pages": [
    {"id": "待补充", "name": "待补充"}
  ],
  "scenarios": [
    {"id": "待补充", "entry": "待补充", "flow": ["待补充"]}
  ],
  "states": [
    {"id": "待补充", "description": "待补充"}
  ],
  "decisions": []
}
</script>
```

上例只定义生成形状，不另立字段、枚举或完整性词表；完整合同以 [上下文加载合同](../../references/context-loading.md)「prototype-meta 完整性与 HTML 降级」为唯一权威。所有业务值必须来自当前需求摘要、决策账本和用户确认，禁止沿用示例占位。Confirmed metadata 的真实业务字段若仍是「待补充 / 待确认 / TODO / TBD / PLACEHOLDER / 示例」等精确占位值，必须判为 `INCOMPLETE`；`decisions[].status=待确认` 仍是合法业务状态。

元数据必须与页面实际表现一致，只记产品决策，不记前端实现细节；不记不存在的确认结论。每轮修改同步更新，确认后将 `prototypeStatus` 更新为 `Confirmed`。确认前必须运行 metadata 提取检查；只有 `COMPLETE` 且至少包含页面、主场景和默认或业务状态，才能作为 required 路径的正式原型证据。`INCOMPLETE` / `INVALID` 必须修复；历史原型按共享合同定向核验 HTML、补齐并重新分类，不能以“历史兼容”为由直接进入 PRD。元数据内嵌于 `index.html`，不额外生成 JSON 文件。

## 9a. 原型阶段返回合同

原型确认后返回：原型版本、`prototype-meta` 完整性结果、页面/场景/状态/交互证据、新增或变更的 `D-###`，以及是否需要同步需求摘要。正式豁免由协调 Agent 返回豁免原因、批准人和时间。协调 Agent 在摘要确认且原型确认/豁免后据此生成 PRD 阶段快照；本 Skill 不生成快照。

## 10. 基础信息

原型评审信息至少含：需求名称、原型版本、原型状态、创建人/发起人、创建时间、目标设备、目标平台、当前模块、本次包含范围、本次不包含范围、已确认决策、待确认问题。无法获得的信息写「待补充」，不猜测。

## 11. 设备与移动端适配

默认设备 iPhone 16；逻辑尺寸 393 × 852；竖屏；目标平台 iOS、Android。横屏品类（射击、MOBA、横版动作、赛车等）须先与用户确认朝向再生成。页面应模拟移动端安全区域；核心操作不被评审工具栏遮挡；返回/关闭路径可用；不只适配桌面宽屏。浏览器展示可有手机外框，但外框不是正式 UI；不模拟完整系统状态栏、刘海、导航手势等无关细节。

## 12. 迭代方式

每轮在当前 `index.html` 上更新，不默认新建前端工程或多套并行文件，不建 `v0.1/ v0.2/ v0.3/` 目录；历史变化由共享工作目录、阶段状态和 Git 记录承担。每轮输出：原型版本、本轮修改、受影响页面、受影响决策、新增或解决的待确认问题、更新后的 `index.html`。确认后冻结为 `Prototype vX.Y - Confirmed`。冻结后未重新确认不得改变：页面范围、主流程、核心按钮、确认步骤、弹窗结构、关键状态、已确认业务决定。

## 13. 异常处理

出现以下情况不得自行补全，应输出冲突内容、来源、对原型的影响、推荐方案、需协调 Agent 或用户确认的问题：

- 需求摘要与决策账本不一致；
- 原型需要一个尚未确认的核心规则；
- 历史 UI 与用户最新决定冲突；
- 当前模块边界不清；
- 某状态会改变商业模式、付费规则或核心流程；
- 已确认原型修改会使需求摘要失效。

## 每轮输出

- 原型版本
- 本轮修改
- 受影响页面
- 受影响决策
- 新增或解决的待确认问题
- 更新后的 `index.html`
- 可携决策片段：状态机/页面结构/交互时序等比散文更精确编码的决策，供 PRD 内联（见 prd-spec.md「实现边界与原型交接」）

## 交互原型确认门

原型必须能实际点击并覆盖关键状态。只有用户明确表示“页面可以”“交互确认”“按这个方案做”或“可以生成 PRD”后，才能冻结为 `Prototype vX.Y - Confirmed`。

冻结后写入共享工作目录，交由编排器更新产物版本和本需求目录的变更记录（若存在），随后进入 PRD。

若作为窄任务独立调用，直接输出可运行原型与待确认问题，不写正式流程状态或需求变更记录。

评审若改变关键页面、主路径、确认步骤、弹窗结构、核心按钮状态或关键页面状态，返回本阶段并重新确认。
