# NPC 系统

更新时间：2026-07-26  
状态：目标架构  
负责人：吴正伟

## 1. 模块定位

NPC 系统采用数据流和事件驱动架构，形成：

```text
生成
→ 模拟/更新
→ 玩家或系统交互
→ 关系/剧情变化
→ 反馈、结束或衍生事件
```

## 2. 数据边界

- 冷数据：NPC 模板、人格、MBTI、对话风格、模型、职业、成长、关系、功能、物品、事件和 Agent 配置。
- 热数据：NPC 实例、当前状态、关系、资产、槽位账本、事件实例和审计日志。
- 冷数据经 AI 辅助和人工审核发布后，运行时只读消费。
- 热数据由服务端写入和更新，不由 AI 直接持久化业务结果。

## 3. 开发与算法职责

开发/服务端负责：

- 规则与事件评估
- 容量、唯一性和约束校验
- NPC 实例、槽位和账本
- 资产、关系、事件效果和奖励结算
- 幂等、事务、日志和审计

算法/AI 负责：

- 对话、行为和意图推理
- 人设与表达增强
- 内容建议和降级建议
- 批量生成的限流与回退策略

AI 不得越过服务端规则决定资产、关系、奖励、任务状态或最终效果。

## 4. NPC 资产与背包

- NPC 资产具有生成、展示、消耗和回收生命周期。
- 赠礼、回礼和红包由服务端先确定资格、价值和实际资产，再由 AI 按人设生成表达。
- NPC 可在关系和权限满足时向玩家透露资产信息；具体概率、阈值和去重策略属于配置或规划候选。
- 死亡掉落、幽灵资产等仍属未来方案，未正式确认前不得作为稳定规则。

## 5. 配置原则

- 优先合并生命周期一致的 1:1 扩展表。
- 同域规则表可以合并，但类型和目标必须用显式字段区分。
- 1:N 变体表不得强塞入主表。
- 公共字典和公共能力保持独立。
- 保留强字段结构，不把关键规则隐藏在不可检索的 JSON 黑盒。
- 保持多语言、Excel 导出和 SQLite 导入链路兼容。

## 6. 模型商业化分流

已确认方向：

- 高频、结构化判断优先使用小模型或分类器。
- 系统决定任务、资产和规则，模型负责表达包装。
- VIP/陪伴权益可提供更强表达、长期记忆或高阶 TTS。
- 免费层仍必须保证基本可聊、流畅、逻辑正确和安全。

具体模型规模、供应商、触发比例和记忆轮数属于可替换实现，不写成长期固定事实。

## 7. 新需求检查

- 是否复用现有模板、关系、事件、功能和资产结构。
- 写入的是冷配置还是热状态，发布和审计责任归谁。
- AI 输出失败、超时或降级时，权威业务结果如何保持。
- 是否影响 NPC 事件日志、关系、资产、记忆和成本。
- 是否引入新的 1:N 配置或 JSON 黑盒。
